## FastAPI에서 def와 async def의 차이

핵심 개념: 이벤트 루프, 스레드 풀 실행, 블로킹 호출의 위험, 비동기 라이브러리, CPU 바운드 작업

- 이벤트 루프: `async def` 경로 함수는 이벤트 루프(메인 스레드)에서 직접 실행된다. `await`로 I/O를 기다리는 동안 이벤트 루프가 다른 요청을 처리하므로, 스레드 하나로 많은 요청을 동시에 다룰 수 있다.
- 스레드 풀 실행: `def` 경로 함수(와 `def` 의존성)는 FastAPI가 AnyIO 스레드 풀의 작업 스레드에서 실행한다(기본 최대 40개). 그래서 안에서 블로킹 호출을 해도 이벤트 루프를 막지 않는다.
- 블로킹 호출의 위험: `async def` 안에서 `time.sleep()`, `requests`, 동기 DB 드라이버처럼 블로킹 호출을 하면 이벤트 루프 자체가 멈춰서 그동안 서버 전체의 다른 요청이 모두 기다린다.
- 비동기 라이브러리: `async def`의 이점은 `httpx.AsyncClient`, `asyncpg`, `AsyncOpenAI`처럼 `await`할 수 있는 라이브러리로 I/O를 기다릴 때 생긴다. 동기 라이브러리만 쓴다면 `def`가 안전하다.
- CPU 바운드 작업: 계산이 오래 걸리는 작업은 `async def`든 `def`든 해결되지 않는다. `async def`에서는 이벤트 루프를 막고, `def`의 스레드 풀은 GIL 때문에 병렬로 계산하지 못한다. 프로세스 풀, 작업 큐(Celery 등), 워커 프로세스 여러 개로 나눠 처리한다.

흔한 오해:
- "`async def`로 쓰면 항상 더 빠르다" → `await`할 I/O가 없거나 동기 라이브러리를 쓰면 이점이 없고, 블로킹 호출이 섞이면 오히려 서버 전체가 느려진다.
- "`def` 핸들러는 이벤트 루프를 막는다" → `def`는 스레드 풀에서 실행되므로 막지 않는다. 막는 것은 `async def` 안의 블로킹 호출이다.
- "`async def` 안에서 동기 함수를 호출해도 FastAPI가 알아서 스레드로 넘긴다" → 넘겨 주는 것은 경로 함수와 의존성 단위다. 함수 안의 동기 호출은 `run_in_threadpool`이나 `asyncio.to_thread`로 직접 넘겨야 한다.

심화 포인트:
- 스레드 풀 크기는 기본 40이라, 블로킹 `def` 요청이 40개를 넘으면 나머지는 빈 스레드를 기다린다. AnyIO의 기본 리미터 값을 바꿔 조정할 수 있다.
- 로그에 현재 스레드 이름을 찍으면 `async def`는 `MainThread`, `def`는 작업 스레드 이름이 나와서 실행 위치를 확인할 수 있다.
- 여러 CPU 코어를 쓰려면 Uvicorn 워커 프로세스를 여러 개 띄운다. 프로세스마다 이벤트 루프가 하나씩 있다.
